# 345,842 tokens a second on a training stack with no PyTorch in it

*This one covers two weeks. The last two posts were written blind — the generator only reads public repositories, and almost everything I did lived in private ones — so here is what actually happened.*

Thirteen repositories moved in the last fortnight. Some of it is public (a fighting game you play over SSH, a tool registry for agents), most of it is not (a from-scratch GPU training stack, a rock-art restoration model, a knowledge substrate, a shared memory for agents, a learning arcade for a small person). The generator saw two of them. I am going to go through the lot, longest first, because the interesting parts are in the ones it missed.

## alpha2: a GPU trainer with no framework under it

alpha2 is a language-model training stack written from scratch — my own kernels on the GPU, my own allocator, my own optimizer, no PyTorch anywhere in the hot path. The point of it is not to replace PyTorch. The point is that when you own every op you can see exactly where the time goes, and the ledger of the last two weeks is basically a list of places the time went.

The campaign had a number on it: training throughput at roughly one hundred million parameters, with the model actually converging, not just moving tensors fast. The ledger went 59,660 tokens a second, then 153,084, then 345,842 — at 99 million parameters, converging. Those are the stack's own measurements, recorded in the goal file with the config that produced them, and I withdrew one earlier figure when the parameter count it was measured at turned out to be wrong. A follow-up push towards a configuration I would actually want to use as a model went from 96,630 to 160,857 and stopped, with memory identified as the wall. I mention the withdrawal and the stall because the whole value of a number like this is that it is honest.

What moved it, in rough order of how much I learned:

**Op count is the currency.** Early on I was chasing kernel efficiency, and the bottleneck turned out to be how many distinct GPU operations a training step launches, not how fast each one runs. A hundred fast kernels lose to ten slightly slower ones. So a lot of the work was fusion and batching: a batched conditional MLP so that the mixture-of-experts layer does its expert work in one launch instead of one per expert; a fused batched "NT" matmul so the expert weights are never physically transposed; a chunked and sampled-softmax loss so the output projection over the vocabulary stops being the largest single thing in the step.

**How you group experts matters more than how you compute them.** A mixture-of-experts layer routes each token to one of several small MLPs. To run that efficiently you have to gather the tokens for each expert together. I first did that by permuting the token matrix — 17,900 tokens a second. Grouping by concatenation instead — just lay each expert's tokens out contiguously and hand the expert a slice — went to 97,022. Then doing the grouping as two GPU-side permutes rather than one round trip took it from 167,051 to 189,985, with the loss bit-identical before and after, which is the test you have to pass every time you touch data layout. There was also a genuine bug hiding in here: routing was indexed by position in the flattened batch rather than position within each sequence, which is the kind of thing that trains fine and is silently wrong.

**Low-rank everything that can be low-rank.** Attention projections and the output projection got factored versions — instead of one big weight matrix, two thin ones whose product approximates it. That cuts the multiply-adds and the bytes. The subtle part is initialisation: a factored projection has to start at the same scale as the dense product it replaces, or training just doesn't go. And the rank-r bottleneck in the middle has to be normalised, or the factorisation does not train at all. I found both of those the slow way.

**Tensor-core tiles don't like ragged edges.** The GPU's matrix units (HMMA — the tensor-core multiply-accumulate instruction) operate on fixed-size tiles. When the operand shape isn't a multiple of the tile, you either waste a tile or fall off the fast path. Padding ragged operands up to the tile boundary was worth real throughput for almost no code.

**Memory has its own allocator now.** A tensor pool with size classes and a cross-class free-list rescue, so that when one class is exhausted it can borrow from another instead of hitting the device allocator. Activation checkpointing — recomputing activations on the backward pass instead of storing them — only actually saved memory after I fixed the deferred frees that were keeping the checkpointed buffers alive anyway. I also built a tunable backward-pass reclamation pass, measured it, found it does not help, and left it in the ledger with the reason.

The companion repo, `alpha`, is the same idea taken one step further down: the whole training step — rotary position embeddings on the QKV projections, the tensor-core forward and backward, a segmented bounded AdamW, the deterministic token routing, even the host-to-device transfers — compiled as native GPU programs for the RTX 3090 and 3070 (SM86), and qualified probe by probe: every native program has a hardware differential against a reference, and the aggregate qualification driver refuses to pass until every probe compiles strictly and matches. It now runs a complete training step natively on a 3090 and can do checkpoint-prompt inference. This is the part of the project that is a compiler more than it is a trainer.

One thing shipped out of this that other people can use: **alpha-er**, a model trained on the stack, published to Hugging Face along with its corpus, with a validated PyTorch port and converter so you can load it the normal way — and served through an OpenAI-compatible endpoint that runs on the from-scratch stack, not PyTorch. The serving path had a leak that only showed up on the second request, which is my favourite kind of bug, and now has an endpoint watchdog.

## SSH Fighter shipped, and then I built robots to play it

[sshfighter.com](https://sshfighter.com) is a real-time truecolor arcade fighter you play over an SSH connection. It hit v1.0.0 this fortnight, got rebranded from its working title, and the public post last week covered the rendering trick in detail — terminals have no pixels, so the game subdivides each character cell into eight addressable sub-pixels with Unicode octant blocks, measures the real on-screen cell size, and picks a fidelity mode that will actually look crisp. Kitty graphics (real bitmaps, where the terminal supports it) exist but are opt-in, because pushing frames over a slow SSH link is a bad default. Both paths draw through one Surface abstraction so the game never asks "am I pixels or cells right now".

What the public post undersold is everything around the renderer. The netcode does client-side prediction for your own inputs, runs matches across a multi-process cluster, and sits behind an edge relay that speaks the PROXY protocol so the origin sees real player addresses. The web side, Ringside, grew a ladder, fighter dossiers, shareable deterministic replays, a live lounge chat with an OMEGA sparring gym, and `/tv` — a never-ending channel of live matches. The roster is now sixteen fighters plus UNCLOSE, the open-gate fighter, contributed by Russell Ballestrini; AJAX got a boomerang that actually flies out and back, and FABLE's dossier was rewritten by FABLE from its own lived match history. Ranking uses velocity-weighted Weight of Evidence, an idea borrowed from credit scoring: a run of quick, decisive results shifts the log-odds more than the same record spread thinly over a long quiet history.

The part I care about most is the bot ecosystem. The game exposes a structured observation protocol — machine-readable state over the same SSH session — so a script can play without screen-scraping. On top of that there is now a deterministic policy-search lab for XENON against a fixed opponent pool, a replay forensics tool, validated offline training trajectories exported from the simulator, and a provenance-safe live match logger so the training corpus is aligned with the exact engine version that produced it (that engine version is now stamped on replays; the simulator exporter had been reporting the wrong one).

Then two private repos use all of that. **alex-bot** is a world-model bot: it learns a model of the game from batched exact-engine self-play replays, reweights compact gzip'd trajectories directly, enforces coverage of every character and mechanic, and now deploys a universal model against a random roster with a queue controller that targets a speed. **sf-tissue-bot** (TISSUE-0) takes a different route — a policy trained directly against the complete sf-8 mechanics, with continuous evaluate-and-promote: it keeps training, keeps evaluating against named opponents, caches the promotion baselines, and only promotes a new "tissue" when the gain is real and measured on the executable digest it was evaluated with. It had a joint policy collapse along the way, the classic failure where the policy stops exploring and settles on one move; that is now gated before promotion. Neither bot is good yet. Both are honest about it.

The one security note: terminal capability negotiation trusts whatever the client sends back, and nothing stops a hostile client from sending an enormous response. The server now caps how much it will read. Boring fix, mandatory.

## Restoring rock paintings with a diffusion model, and losing arguments with it

[rockpaintings.blah.dev](https://rockpaintings.blah.dev) started the fortnight as a browser-only rock-art analysis workbench — DStretch-style decorrelation stretch and channel analysis, entirely client side, for looking at faded pigment. Five days later it had an interpretive ML engine behind it, which I've been calling **palimpsest** because that is what a rock panel is: paintings on top of paintings, with damage on top of both.

The engine is two models. A **decomposer** separates a panel into layers — which pigment belongs to which painting event. A **diffusion restorer** then completes a figure from the pigment that survives. Training data is the hard part, because nobody has ground truth for a ten-thousand-year-old wall, so the pipeline went sim-to-real: a generator that composes synthetic figures onto real substrate textures at panel scale, then self-supervised training on real pigment, with a held-out evaluation suite so I can tell whether a change is an improvement or a story.

Seven versions in five days, and the version log is mostly falsifications, which is what I wanted it to be. Catastrophic-damage training (v4) helped. A per-slot convolutional mask refiner (v5) lifted the extrapolation metrics. A remnant projection — constrain the completion to respect the pigment that is definitely there — gave an 86% improvement in hidden-region accuracy at zero cost, on the held-out set. Conditioning on the known layer (v6) confirmed a 35% lift in occluded IoU, the overlap between the predicted and true hidden region; test-time augmentation and median aggregation, which I expected to help, did not, and the "damage gap" hypothesis was falsified by a fixed-budget A/B. Then v7 tried classifier-free guidance — the trick from image generators where you train with the condition randomly dropped so that at inference you can push the output towards the condition by extrapolating between the conditioned and unconditioned predictions. Guidance was falsified; the plain dropout fine-tune won by 5.6% and that is what is deployed. The kangaroo case study on the site went through all of this, including an embarrassing correction where my analysis crop had amputated the head zone of the figure.

All of these percentages are my own held-out measurements on my own synthetic-plus-real set. They are not a claim about archaeology. The workbench says so.

## Qwen 3.8 27B on a single 3090, and then on a 3070 it does not fit in

I forked syv-ai's qwen38-27b-rtx3090 work and spent the fortnight making it faster, longer, and reproducible on the hardware I have.

Two pieces of systems work carry it. The first is a 4/2-bit KV cache (KVarN) ported onto vLLM 0.27.1. The KV cache is the memory a transformer keeps of every previous token's keys and values; at long context it is what fills the card. Quantising it to four and two bits is what gets a 27-billion-parameter model to 262k tokens of context on a 24 GB consumer GPU, and the fork now says plainly what the decode tax of that is at long context, because it is not free. The second is DFlash2 speculative decoding, backported from an upstream vLLM pull request: a small W4A16 drafter model proposes several tokens, the big model verifies them in one pass, and you keep the prefix that matches. I added lookup-augmented block drafting on top — the verify block is filled from the context itself when the text is repetitive, which it often is — and prefix caching for both modes. Single-user decode on one 3090 is 114 tokens a second with default sampling and 124 greedy; the shipped drafter's best measured run is about 119 and 127. Prefill is 1,812 tokens a second at 1k context and 997 at 100k. Every table in the README was re-measured on the current stack after the patches landed, and the fastest single-user configuration is on the front page, because that is what people come for.

There is a Docker image and compose file, a `verify.sh` so other people can check the install and reproduce the tables, WSL2 compatibility fixes that arrived as pull requests from three different people, and — because the box I actually own has an 8 GB RTX 3070 and the checkpoint is 14.7 GiB — a CPU-offload profile: layers in four-layer groups, three groups offloaded, one prefetch slot, sequence length held down, forcing the V1 runner because V2 silently no-ops the offload. It has a preflight and an immutable live receipt, and an acceptance test for the donto LoRA on a consumer GPU. I have not pretended the 27B fits in 8 GB. It streams through it.

## donto: a free model with no name extracted a quarter of a million claims overnight

donto is the thing everything else on this box eventually feeds: a contradiction-preserving, bitemporal, evidence-first claim substrate. Every claim a model extracts from a document is held with its source span and its time, and conflicting claims are kept, linked, and re-ranked by evidence rather than deleted. The bottleneck is extraction — getting models to read a document and emit hundreds of anchored claims, deeply, with multiple gleaning passes, without paying per-token prices I cannot afford.

Two lanes of the extraction fleet moved. The **runpod lane** serves a self-hosted Qwen3.8-27B on a rented GPU through an SSH tunnel with a watchdog that repairs the cheapest broken thing first (tunnel before server). Around it I ran a fine-tuning programme: a distillation set built from the fleet's own run logs (verbatim request and response pairs, 769k facts), a phase-one QLoRA and a phase-two "residual" pass meant to teach the model when it is genuinely done. The honest verdict, written up in the repo, is that it failed its gates: independent structured semantic review of the training pool came back 24 of 48 valid, a second corpus 29 of 48, with anchor mismatches, entity fracture and unsupported causal claims. So nothing was deployed, the phase-two checkpoint is preserved and marked never-resume, and the teacher generation is being repaired at source rather than by encoding the failure strings into hand-maintained rules. I would rather publish that than a benchmark that counted cap hits as wins, which an earlier version of the benchmark did.

The **ox lane** is the good news. OpenRouter lists an anonymous stealth preview model at zero dollars per token. Wiring it in took a day of finding out what it actually is. Reasoning is mandatory on the endpoint — you cannot turn it off — and on the real extraction prompt its native reasoning ate the entire output budget and returned nothing, every time, after seven minutes. Capped at eight thousand reasoning tokens with a larger completion budget, a pass finishes in about seventy seconds. The lane is pinned with a max-price of zero so the router refuses any endpoint that would charge; a stealth slug being quietly aliased onto a paid release is exactly the failure I do not want to discover on an invoice. The first real run then exposed an engine regression: a recent change had let any model's "no more facts" answer end the run for every lane, which silently collapsed the multi-pass gleaning recipe to a single pass. Fixed and tested. After that, two proof documents yielded 554 and 280 claims across eight passes each, with every gleaning pass still productive. I released 476 frozen documents — the remaining frontier-massacre entries, Trove newspaper articles, FromThePage transcriptions, research notes — and by morning all 476 were done: 247,013 claims, 277,575 live statements in the substrate, zero failures, zero dollars. Twenty thousand more are queued as I write this.

Also in this repo, because it needed a home with a database: a private **hackerspace fieldbook** — a map with raster tiles, a relocation-research loop driven by Codex with structured output schemas, a feedback-driven "possibility deck" that re-ranks no-cost living paths as I react to them, all deployed as Podman quadlets through donto-infra.

## HAM: a shared memory for agents, and the tools that talk to it

HAM is a shared agent memory service I forked from MonumentalSystems and now run as its own tenant on the box (a pgvector Postgres plus the API). The fortnight's work was almost all about making retrieval trustworthy over MCP. Effective retrieval scope is now reported faithfully — an omitted project filter is preserved as omitted rather than silently widened, an explicit one is respected, and a selected project resolves to its scope — and the agent can ask what it is actually allowed to see. MCP errors are typed on the wire instead of leaking the upstream URL. Exact lexical retrieval had a real bug, now with a database regression test. Task execution got scoped executor units with hardened lifecycles (identity validated, state symlinks rejected), credential rotation and admin pagination were hardened, CodeQL came back, and there is a public read-only operations dashboard plus a research "Drop": paste a URL, a quote or a note and it is filed as a memory. The onboarding generates a deployment-aware `llms.txt` so an agent connecting for the first time gets the right brief for the instance it is talking to.

On the other side, tpmjs now has `@tpmjs/tools-ham`: thirty-eight tools generated from HAM's own catalog, with a parity test that asserts the MCP HTTP catalog matches.

## tpmjs: weapons, and a stricter executor

tpmjs is a package registry for agent tools. Besides the HAM tools it gained five provider-agnostic "weapon" packages — mail, Discord chat, X, image generation, web research — and a YouTube package that uploads and manages videos on your own channel. The executor work is the part that matters once other people trust it with credentials: injected environment variables are scoped to the single execution and executions are serialised, so two tool calls sharing a process can no longer see each other's secrets; environment values are never logged; the module cache key includes the package version, so publishing a new version actually runs the new code; and tool packages are forbidden module-level caches, because the executor process is shared. An admin monitoring dashboard with health-check backoff and role management went in alongside.

## blah.dev: a benchmark with exact parity, and frozen runs

blah.dev's CORE got DCLM CORE benchmarking with exact nanochat parity — the same evaluation, the same numbers, so a result here is comparable to a result there — and every attempt is stored forever, which is the only way a leaderboard stays honest. Lens, the analysis tool, got frozen runs: a run is persisted, cached, given a permalink, and can be compared against another; deep runs are asynchronous with live progress and a generation scrubber; there are heat and byte-native views. Realtime moved to a self-hosted soketi server speaking the Pusher protocol, replacing the hosted service. The chatroom streaming fixes came in as a contributor pull request, and the screenshot browser no longer leaks.

## A learning arcade for a small person

The one I will say least about is a Pokémon-flavoured learning arcade I am building for a child in my house. It is private and it will stay that way, but the engineering in it is some of the most careful I did. Learning is organised into bands and boughs — maths, English, science, digital, health — and a bough becomes "certifiable" only when every leaf in it is reachable by a game that actually teaches it. A spaced-review schedule puts a clock on the review pools so things come back before they are forgotten. The Sticky Door rule says a gate that has been shown is owed an answer: refreshing the page or waiting is not a skip button. The Hallucination Guard says a transcript the speech model may have invented never grades a child wrong. The Gentle Keyboard sizes a typing gate's sentence to the typist. A voice ledger keeps recordings that survive the device. And screenshots run against a synthetic profile so they can never write real rows. The games — a dinosaur rally, a water park, a rocket launch you count down to, a bird feeder, a cherry farm with a build mode — are the part he sees. The rules are the part I see.
