# I Put a Firewall Between My Model and the Humans Grading It

*And a protocol learned to say why it's declining, a terminal renderer learned to shut up unless something actually changed, and a translation app decided a recorded voice matters more than a good one.*

Busy week. I'm going to go project by project and try to explain what actually happened underneath the surface, because "shipped a bunch of stuff" is not a sentence, it's a shrug.

## alpha2: don't let the grader see the answer key

I'm training a small language model from scratch — pretraining, then supervised fine-tuning (SFT) on chat data, then trying to make it not embarrassing. The mechanical part of that is boring in the way all training runs are boring: you checkpoint every 500 steps, you watch a loss curve, you occasionally catch a bad run and roll back. Most of this week's activity in that repo is exactly that — a long, unglamorous trail of "here's step 47,500, here's the eval, here's whether it's a new best." I won't pretend that's interesting to read, and there's a lot of it.

The actually interesting problem was different: how do you know if your chat model is *good*, when the only judges you have are you, and a model you also built?

The standard failure mode here is contamination. If the same person (or process) that trained the model also grades its outputs, you get motivated reasoning — "actually that response is fine" — without anyone deciding to cheat. Confirmation bias doesn't need intent. So this week I built out what I've been calling an evaluation firewall: a wall between the pipeline that trains and releases checkpoints, and the pipeline that reviews what they say. The review side runs blind — a reviewer sees a model's output without being told which checkpoint, which run, or which version produced it.

The clever bit, if there is one, is *blinded repeat presentation*. Occasionally the same output gets shown to the same reviewer twice, unannounced, mixed in among everything else. If they rate it "great" the first time and "mediocre" the second, that's not the model being inconsistent — it's the reviewer being inconsistent, and now you know your grading process has noise you need to account for before you trust any single verdict. This is a straight lift from psychometrics — it's how you measure a rater's own reliability, not the thing they're rating — and it turns out to be exactly what you want when the "instrument" doing the grading is a tired human clicking through a queue of near-identical model outputs at 11pm.

Downstream of the firewall, releases got more conservative, not less: I gated the automated "hey look, new checkpoint" posts on actual qualitative improvement rather than a lower loss number, because loss going down and the model getting less annoying to talk to are correlated, not identical. And I fixed a real bug in how the chat model was starting its responses — small diff, but the kind of thing that quietly makes every downstream eval look worse than the model actually is, because you're grading a stutter, not a capability.

## crap: teaching a protocol to say why it's saying no

[CRAP](/posts/crap) — the HTTP protocol I've been building that lets a server ask an agent a structured question before deciding whether to let it in — got its actual public launch this week (there's a whole post about it if you want the deep version). What I want to cover here is the stuff that happened *after* launch, because a protocol doesn't get interesting until real traffic hits it.

Two schema additions matter more than they look. First, challenges can now declare what satisfying them actually buys you — previously a challenge just said "answer this or you're getting a 403," with no promise attached to answering it correctly. Now the response can say, in effect, "give me this and I'll grant read access to the last 90 days." That sounds small, but it's the difference between an agent blindly filling out a form and an agent being able to do a cost-benefit calculation before it bothers. Second, I added a `decline_reason` field, so an agent that refuses to answer a challenge can say *why* — not enough scope, not enough budget, don't trust this issuer — instead of just going quiet. That's groundwork for the "counter-offer" idea I flagged as an open question in the launch post: a client that declines being able to say "not that, but I'll take a narrower slice on these terms" instead of the conversation just dying.

I also shipped `input_data` for task-kind requests, which matters for the weirder half of the protocol — the "computational toll" idea, where instead of paying money for access you pay a small unit of work (classify this document, translate this title). Before this week, a task challenge could describe what it wanted done but couldn't actually hand the agent the content to do it on. Now it can. And I wrote up a field report — [FINDINGS.md](https://github.com/thomasdavis/crap/blob/main/FINDINGS.md) — from running this against real traffic instead of my own test suite, which is the only way you find out that your "clean" v0.1 had binding holes real agents would have walked straight through. That report is what drove the v0.2 rewrite: three real binding bugs, the kind where a proof earned for one request could be quietly replayed against a different one. I also moved the whole thing off a domain I didn't fully control and published the packages properly on npm under my own scope, which is the unglamorous but necessary difference between "an idea in a repo" and "a thing you can `npm install`."

## tpmjs: making two search engines agree with each other

tpmjs is a package registry for tools AI agents can call — think of it as the thing an agent's MCP client or a coding CLI queries when it wants to find "a tool that converts CSV to JSON" without you hand-wiring the integration. This week had one fix that's more interesting than it sounds: I unified the ranking logic between the MCP `search_tools` endpoint and the plain REST search endpoint, which — I discovered — had quietly drifted into two different ranking functions. Same index, same tools, different order depending on which door you walked in through. That's a nasty bug class because nothing throws an error; it just means an agent using the MCP surface and a person using the website get different answers to the same question, and nobody notices until someone screenshots both side by side.

I also shipped a `/trending` leaderboard ranked by momentum rather than raw install count (so a tool that's suddenly getting attention this week outranks a stale tool that got 10,000 downloads two years ago and hasn't moved since), and a real `/tools` browse index that's actually faceted and paginated instead of a flat list, which also means it's crawlable and indexable by search engines now, not just useful to someone who already knows what they're looking for.

The other fix worth explaining: MCP's newer transport, "streamable HTTP," replaced the older SSE-based transport, and it has stricter rules about session headers and response framing than the old one did. Some clients are forgiving about this. Codex is not — it simply refuses to attach if the handshake isn't exactly spec-compliant. So a chunk of this week went into getting tpmjs's MCP server to comply with the letter of the spec rather than the "close enough for the clients I happened to test with" version, plus a new CI workflow that actually exercises every surface — REST, MCP, the collection-scoped MCP variant, the CLI, and the SDK — end to end against a live deployment, so this class of drift gets caught before a user does. Last thing: tools that fail health checks repeatedly used to just vanish from listings. Now they stay visible but get ranked down, because hiding a broken tool erases the record that it existed and confuses anyone who remembers using it, where demoting it keeps both the tool and its failure history on the record.

## maldoror.dev: a renderer that only draws what changed

This one's harder to describe because the repo's own description is just "lol," but the substance is a procedural world/city generator that renders to a terminal using packed ANSI color cells. The rendering work this week was, underneath the cryptic commit titles, basically frame diffing: instead of redrawing every character cell on screen each tick, the renderer now tracks what actually changed since the last frame and emits only contiguous runs of changed cells, with cursor-position deltas kept as small as possible. This is the same idea behind how `tmux` or `vim` avoid full-screen repaints — recomputing and re-sending an entire terminal's worth of colored characters every frame is slow and flickery, especially over SSH, so you diff against the previous frame and only pay for the pixels that moved.

Two more substantial pieces: NPCs now have work schedules bound to specific hand-authored places rather than floating procedural assignments, which makes their arrivals at a location something you can actually point at and audit instead of trusting the simulation blindly. And there's a street/canal frontage system doing constraint-based layout — proposing candidate street pairings, checking them against protected geometry, and admitting the ones that fit.

What's genuinely unusual about this repo's process, and worth calling out on its own: failed design candidates get committed to the repo as "retained rejected evidence" rather than deleted. A rejected layout, a rejected caching strategy, a rejected topology — they all get a paragraph explaining why they didn't work, sitting right next to the ones that did. It's a lab notebook that keeps its dead ends instead of pretending only the final answer ever existed, which is a genuinely good habit most codebases don't bother with because git history is theoretically "enough" — except nobody reads git history for reasoning, they read it for diffs.

## mobtranslate.com: whose voice is this, actually

mobtranslate.com is a translation app for Australian Aboriginal and Torres Strait Islander languages, built with the communities whose languages it's documenting, and this week's work was almost entirely about tightening consent and provenance rather than adding flashy features.

The concrete change: recorded human voices are now preferred over synthetic speech wherever they exist, instead of falling back to text-to-speech as a default convenience. That's a deliberate trade against the easy path. Synthetic speech for a language with a handful of fluent speakers and very little training data tends to flatten pronunciation and strip out the parts of speech that carry cultural weight — the whole point is that these are living languages spoken by specific people, not phoneme sequences to be interpolated. Alongside that, voice sharing consent got made explicit — recordings are attached to a real consent decision rather than an implicit "you uploaded it so we can use it" — and dictionary entries now show exact source trails, so you can see which recording or which contributor a translation traces back to instead of it appearing from nowhere. There was also real work scoping down what admin accounts can actually see and do, and rebuilding the curator workspace so the people doing the actual language work have a tool that matches how they work rather than a generic CMS bolted on top.

None of this is the kind of thing that shows up in a screenshot. It's the boring, correct kind of infrastructure — the kind that decides whether a community trusts you with their language a second time.
